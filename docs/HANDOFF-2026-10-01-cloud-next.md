### 2-4. 🚫 «입찰 전 고객–업체 연결»을 만들지 않는다 (대표 결정 2026-09-30)

**고객이 입찰을 고르기 전까지 업체와 연결하지 않는다.**
입찰 전 채팅도, 요청에 붙는 공개 Q&A 도 만들지 않는다.

**왜 이 결정이 맞나** — 저장소에 이미 같은 판단이 들어 있다:
`src/constants/directDeal.js` 의 `detectDirectDealKeywords` 가 **직거래 유도를 잡아낸다.**
입찰 전에 대화를 열면 업체가 「직접 연락주세요」로 빼돌릴 창구를 **우리가 만들어 주는 꼴**이다.
견적 정확도를 조금 올리자고 **플랫폼이 새는 구멍**을 뚫는 것이라, 안 하는 게 맞다.

**다음 세션이 이렇게 생각할 수 있다** — 「업체가 입찰 전에 물어볼 데가 없어서
짐작으로 숫자를 던진다. 요청에 Q&A 를 달자.」 **문제 인식은 맞지만 답이 틀렸다.**
그 문제의 답은 **요청서를 더 잘 받는 것**이다(현장 사진 · 빈 곳 안내 — 09-30 에 넣음).
연결을 앞당기는 쪽으로 풀지 않는다.

> 대화는 지금대로 **계약·공사 화면(EscrowScreen)에서만** 연다.
> 이 결정을 뒤집는 건 대표 말이 새로 올 때뿐이다.

**남은 폰 확인(189·190)**: 라운지 대화함의 보낸·받은·수락됨 목록이 보이는지 → 수락된 방이 열리고 메시지가 오가는지 → 댓글 «대화 신청»에 안내가 뜨는지. 목록이 비면 위 되돌리기 한 줄을 실행한다(앱 배포가 늦게 올라간 경우).

**185 로 열린 것** — 이제 SQL 로 이렇게 물을 수 있다:

```sql
-- 사진이 있는 요청이 몇 건인가
select count(*) from public.requests where array_length(photos, 1) > 0;
```

> 「말한 대로 지수」(입찰가 대비 최종 견적서 차이)를 만들 때 **반드시 이 조건을 건다** —
> `where array_length(r.photos, 1) > 0`. 사진도 범위도 없이 보낸 요청까지 세면
> **요청서를 부실하게 쓴 탓이 성실한 업체 점수로 돌아간다**(대표 지적 09-30).
> 완료 10건이 쌓이기 전에는 만들지 않는다.

**남은 폰 확인(185)**: 요청에 사진 2장 올려 보내기 → 업체 화면에 「📷 …2장」 →
그 요청 **고치기**로 1장 지우고 저장 → 업체 화면이 **1장**으로 줄어드는지
(← 트리거가 도는지 보는 칸. 막히면 되돌리기 한 줄을 만든다)
